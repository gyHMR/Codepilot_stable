# 任务规划控制设计思路

## 设计目标

任务规划控制解决的问题不是“让模型失去自主判断”，而是让一次代码任务有清晰的目标、步骤、证据和完成边界。它应该帮助新手理解 Agent 为什么要做某一步、为什么继续、为什么停止，以及为什么还不能宣称完成。

Codepilot 的任务控制保持轻量：它不是复杂工作流引擎，也不是生产级 FSM。它是一条围绕 Agent 主循环运行的反馈控制链。

```text
用户目标
  -> 任务模式
  -> 当前计划或默认步骤
  -> 工具行动
  -> 证据更新
  -> 完成检查
  -> 任务摘要
  -> 下一轮恢复投影
```

## 核心原则

### 模型负责语义判断

模型仍然负责理解用户意图、选择要读的文件、决定修改方案、解释测试失败原因。任务控制不替模型写业务逻辑，也不替模型决定具体代码应该怎么改。

### 框架负责证据边界

框架负责记录哪些步骤存在、哪些工具结果支持当前判断、工作区是否发生修改、修改后是否有新鲜验证、任务是否仍有阻塞项。模型可以说“完成了”，但框架会检查是否有足够证据支持完成。

### 模式只有少数几个

当前任务模式保持在少数几个用户能理解的口径：

- `read`：只读分析，不修改工作区。
- `edit`：默认开发模式，适合普通修复和小功能。
- `plan`：复杂任务先建立计划，再按步骤推进。

模式不应无限扩张。复杂行为优先通过策略和任务状态表达，而不是新增一堆模式名。

## 任务状态模型

任务状态围绕几个概念组织：

| 概念 | 作用 |
---|---
| 目标 | 用户本轮任务想达成什么 |
| 步骤 | 当前任务被拆成哪些可推进单元 |
| 当前步骤 | 本轮模型应优先关注什么 |
| 证据 | 哪些工具结果、验证结果、文件变化支持状态变化 |
| 阶段 | 当前是在理解、行动、验证、等待还是完成 |
| 下一步建议 | 如果还不能结束，下一步应该做什么 |
| 完成判断 | 是否满足完成条件，为什么 |

步骤状态不只是静态清单。它会随着工具结果更新：

- 读取或搜索成功，说明调查有进展。
- 文件发生修改，说明进入实现阶段。
- 验证通过，说明修改有新鲜证据。
- 工具失败或验证失败，说明需要修复、重试或重规划。
- 权限审批等待，说明任务进入等待用户状态。

## 计划生成与降级

`plan` 模式下，系统可以先让模型生成一个短计划。计划应该短而可执行，最多保留少量步骤，避免让新手面对一棵复杂计划树。

计划生成失败时，不应该让整个任务失败。系统应降级成一个安全的单步任务，并记录降级原因。这样主流程仍然能继续，审计时也能解释为什么没有采用完整计划。

设计上保留几类计划来源：

- 默认计划：简单模式下的轻量默认步骤。
- 模型计划：模型直接生成的步骤。
- 带发现信息的模型计划：先阅读上下文，再生成计划。
- 恢复计划：从上一轮未完成任务恢复。
- 降级计划：计划失败后的安全兜底。

## 完成门控

完成门控是任务控制中最重要的部分。它回答“现在是否可以结束”。

核心规则：

1. 有阻塞步骤时，不能正常完成。
2. 还有未完成步骤时，不能正常完成。
3. 工作区发生修改后，必须有与当前状态一致的新鲜验证，或者明确说明无法验证。
4. 验证失败后，不能把失败结果当完成证据。
5. 权限审批等待时，任务应暂停而不是绕过审批。

这套规则不判断代码是否“优雅”，只判断是否有基本证据支持“任务完成”。

## 失败、修复与重规划

任务控制需要把失败变成可解释的下一步，而不是让模型盲目重复。

常见策略：

- 第一次工具失败：提示模型读取错误信息并修复。
- 验证失败：要求围绕失败断言、日志和相关文件做最小修复。
- 同一步连续失败：考虑重规划或提醒用户可能需要回滚。
- 工具不可用或权限拒绝：进入等待或阻塞状态。

重规划应当是局部的，不应该轻易丢弃已完成步骤和已有证据。学习项目里优先选择“保留已有进度，调整当前步骤和验证步骤”的方式。

## 与其他模块的边界

| 模块 | 任务控制如何交互 |
---|---
| core | 在主循环中维护本轮任务状态，生成任务摘要 |
| sessions | 保存任务恢复投影，下一轮重新注入 |
| tools | 提供工具结果和验证证据，不知道任务策略 |
| context | 把当前任务状态投影进模型上下文 |
| memory | 保存跨任务长期经验，不保存当前任务进度 |
| runtime/interfaces | 只展示任务事件和状态，不直接修改任务内部 |

任务控制不应该直接调用工具执行实现，也不应该直接写长期记忆。它消费工具事实，产出任务摘要。

## 下一轮恢复

任务恢复不是长期记忆。它只保存当前 session 中未完成任务的进度，让下一条用户消息可以继续接上。

恢复数据应该包含：

- 目标。
- 已完成、待完成、阻塞的步骤。
- 当前阶段和下一步建议。
- 完成判断和原因。
- 计划来源和必要发现信息。

如果任务已经满足完成条件，恢复投影就不应该继续激活，避免下一轮被旧任务拖住。

## 设计取舍

当前设计故意不做：

- 大型 FSM 框架。
- 计划树和依赖图。
- 多 planner 模型。
- 自动复杂回滚。
- 自动把任务进度写入长期记忆。

它追求的是一条学生能讲清楚的证据链：

```text
目标是什么
当前做到哪一步
证据来自哪里
为什么继续或停止
失败后为什么修复或重规划
下一轮如何恢复
```
