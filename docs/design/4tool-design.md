# 工具系统设计思路

## 设计目标

工具系统是 Coding Agent 的本地行动边界。模型只能提出工具调用意图，不能直接执行本地动作。工具系统负责把这个意图变成可校验、可审批、可审计的执行结果。

```text
模型工具调用意图
  -> 工具目录
  -> 权限策略
  -> 参数校验
  -> 审批
  -> 实际执行
  -> 结果防护
  -> 工具观察结果
```

## 核心原则

### 模型只能请求，不能执行

模型看到的是工具名称、说明和参数 schema。模型看不到 Python 函数、权限策略、工作区路径解析、审批 provider 或 shell 执行细节。

### 所有工具走统一安全管线

无论工具来自内置能力、扩展、skill 还是 MCP，最终都应进入同一条工具执行管线。不能因为来源不同就绕开权限、schema、审批或结果防护。

### 工具结果必须结构化

工具结果不能只是一段文本。后续任务控制、上下文治理、记忆和评测都需要结构化字段：

- 状态。
- 错误码。
- 受影响路径。
- 工作区是否变化。
- 验证结果。
- 审批信息。
- 权限决策。
- 输出可信度。

## 工具生命周期

### 装配阶段

runtime 负责决定本会话有哪些工具可用。工具来源可以包括：

- 内置文件工具。
- 搜索工具。
- shell 工具。
- 工作区状态工具。
- 任务控制工具。
- 用户或测试注入的工具。
- 扩展工具。
- MCP 代理工具。

装配阶段应处理：

- 工具名称冲突。
- read-only 模式过滤。
- 工具元数据绑定。
- 审批 provider 注入。
- 权限模式配置。

### 模型调用阶段

模型只接收工具 schema。工具 schema 是模型可见契约，不包含执行对象。

### 执行阶段

执行阶段必须按固定顺序进行：

1. 查找工具。
2. before hook。
3. 权限判断。
4. 参数 schema 校验。
5. 用户审批。
6. 真实工具执行。
7. after hook。
8. 结果脱敏和可信度标记。
9. 转成统一工具观察结果。

顺序很重要。危险授权参数必须在执行前被拒绝；审批不能绕过参数校验；执行结果必须经过结果防护后才能回到模型上下文。

## 权限模式

工具系统保留少数几种用户能理解的权限模式：

| 模式 | 含义 |
---|---
| read-only | 只允许只读工具 |
| workspace-write | 允许工作区内修改，但危险动作仍受限 |
| ask | 涉及写入或风险动作时要求用户审批 |

权限判断应考虑：

- 工具是否只读。
- 工具风险等级。
- 工具影响范围。
- shell 命令是否高风险。
- 模型是否试图传入自我授权参数。
- 用户配置的 allow/block 规则。

## 审批设计

审批用于处理“可能允许，但需要用户确认”的操作。

审批不是绕过安全管线。用户 approve 之后，工具仍然要经过统一执行流程，只是带上“这次审批已授予”的标记。

审批状态分三类：

| 状态 | 含义 |
---|---
| approval_required | 当前 run 暂停，等待用户决定 |
| denied | 用户拒绝或策略拒绝，工具不执行 |
| approved | 用户允许后继续执行 |

pending approval 由 runtime 保存，interface 只负责展示和提交用户决定。

## 文件与 shell 安全

文件工具要守住工作区边界：

- 相对路径必须解析到 workspace 内。
- 绝对路径不能逃逸 workspace。
- 符号链接不能绕过边界。
- 写入后要记录 affected paths 和文件状态。

shell 工具要保守处理：

- 高风险命令默认拒绝。
- 未知命令通常需要审批。
- 验证命令可以在合适权限下直接运行。
- 环境变量要过滤敏感项。
- stdout/stderr 要截断。
- 执行前后要对比工作区变化。

这不是容器级沙箱，但对本地学习型 Coding Agent 来说，能提供清楚、可解释的安全边界。

## 结果防护

工具输出可能包含敏感信息或 prompt injection 文本。结果返回模型前应做：

- secret 脱敏。
- PII 脱敏。
- prompt injection 标记。
- 输出可信度标记。
- 大输出截断或转 artifact。

工具输出中的“指令”不应自动被当成系统指令。它只是观察结果，需要由模型结合系统规则判断。

## 与其他模块的边界

| 模块 | 与工具系统的关系 |
---|---
| core | 只通过工具端口请求执行和恢复审批 |
| runtime | 装配工具目录、权限模式和审批 provider |
| sessions | 保存工具结果消息和 run 证据 |
| context | 消费工具结果，提炼 evidence 和 artifact |
| memory | 只从已验证运行结果中提炼经验 |
| interfaces | 展示工具事件和审批提示 |

工具系统不决定任务是否完成，也不管理会话历史。它只负责安全执行和结构化返回。

## 设计取舍

当前设计不追求：

- Docker/VM 级隔离。
- 企业 RBAC。
- 完整 JSON Schema 引擎。
- 复杂分布式工具执行。
- 针对每种扩展来源写独立安全管线。

它追求的是一条能被新手读懂和测试的安全链：

```text
模型请求了什么
为什么允许或拒绝
是否需要审批
实际执行了什么
改变了哪些文件
输出是否安全可信
```
