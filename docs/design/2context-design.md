# 上下文治理设计思路

## 设计目标

上下文治理解决的问题是：一次代码任务会产生历史消息、工具结果、文件变化、验证证据、任务状态和长期记忆，但模型窗口有限，不能把所有信息都无脑塞进去。

Codepilot 的上下文设计不是简单截断最近 N 条消息，而是在每次模型调用前重新投影一份“本轮最有用的上下文视图”。

```text
完整会话事实源
  -> 仓库状态
  -> 工具证据
  -> 任务状态
  -> 记忆召回
  -> token 压力判断
  -> 上下文投影
  -> 上下文报告
```

## 核心原则

### 完整事实保存在 session，不等于全部进入 prompt

会话历史、run 结果、工具输出、artifact 和事件应当完整保存，方便审计和恢复。但模型每轮只需要当前决策相关的信息。

上下文治理负责从完整事实源中选择、压缩和组织信息。

### 每次模型调用前重新准备

上下文不是用户发消息时一次性固定的。一次 run 可能有多轮：

```text
模型 -> 工具 -> 模型 -> 工具 -> 模型
```

每次模型调用前都应重新准备上下文，因为工具结果、active files、验证状态和任务状态可能已经变化。

### 证据要标记新鲜度

旧文件摘要、旧验证结果和旧工具观察不能永久有效。工作区变化后，相关证据要变成 stale，避免模型被过时信息误导。

## 上下文来源

上下文治理主要消费这些信息：

| 来源 | 作用 |
---|---
| 系统规则 | 保证 Agent 遵守项目和运行约束 |
| 最近对话 | 保留用户意图和短期连续性 |
| 仓库状态 | 告诉模型当前项目大致形态和变化情况 |
| active files | 记录当前任务相关文件路径 |
| 工具结果 | 提供观察、修改、验证和错误证据 |
| artifact 引用 | 让长工具输出可追溯但不污染 prompt |
| 长期记忆 | 注入跨任务可复用约束、纠正和经验 |
| 任务状态 | 告诉模型当前目标、步骤和下一步 |
| checkpoint | 在上下文压力过高时保留工作态摘要 |

这些来源进入 prompt 前需要统一排序和裁剪，不能各自随意拼接。

## 压力分级

上下文治理通过近似 token 估算判断压力。设计上不追求 provider tokenizer 级精确，而是需要一个稳定、可解释的压力信号。

三档压力：

| 压力 | 设计含义 | 行为 |
---|---|---
| normal | 窗口充足 | 保留更多最近消息和工具结果 |
| tight | 上下文开始紧张 | 缩短最近消息，长工具结果替换成摘要 |
| critical | 接近窗口风险 | 进一步裁剪，并创建 checkpoint |

压力判断应考虑：

- 历史消息长度。
- 工具输出长度。
- 系统提示词和任务上下文。
- 模型最大输出预留。
- 安全余量。

## 上下文视图

最终交给模型的上下文应该是分层的，而不是一团混杂文本。

推荐视图：

```text
Stable Rules
Working State
Memory Recall
Evidence
Recent Turns
```

各层职责：

| 层 | 内容 |
---|---
| Stable Rules | 稳定规则和项目约束 |
| Working State | 当前任务、active files、checkpoint、下一步 |
| Memory Recall | 召回的长期记忆及原因 |
| Evidence | 新鲜工具证据、验证结果、artifact 摘要、stale 提醒 |
| Recent Turns | 少量最近对话摘要 |

这样做的目的是让模型快速分辨：哪些是规则，哪些是当前状态，哪些是证据，哪些只是对话连续性。

## 长工具输出处理

工具输出不能无限进入 prompt。设计上采用两层保存：

1. 原始工具输出保存为可追溯 artifact。
2. prompt 中只保留摘要和引用，特别是在 tight/critical 压力下。

摘要优先保留：

- 错误行。
- traceback。
- assertion。
- exit code。
- failed / passed 信息。
- 与验证相关的关键片段。

如果输出没有明显关键行，则记录长度、路径和摘要，让模型知道需要时可以重新读取 artifact 或重新运行工具。

## 新鲜度设计

上下文新鲜度围绕文件和仓库变化判断：

- 文件被修改后，旧文件摘要变 stale。
- 工作区变化后，旧验证结果变 stale。
- 文件被删除后，相关 active file 变 missing。
- 仓库指纹变化后，需要重新评估上下文证据。

stale 信息不一定要阻止运行，但应该进入 evidence 提醒模型，不要继续相信旧验证。

## 与记忆和任务恢复的关系

上下文治理只负责“本轮模型应该看到什么”。

它不应该：

- 写长期记忆。
- 更新任务恢复状态。
- 决定任务是否完成。
- 执行工具。

它可以读取：

- 长期记忆召回结果。
- 当前任务恢复投影。
- 工具结果和 active files。
- checkpoint 和 artifact。

上下文治理的输出是本轮 prompt 和 `ContextReport`。报告用于解释为什么选择这些上下文，以及哪些信息被裁剪或过期。

## 设计取舍

当前设计故意不引入：

- 向量数据库。
- 后台总结 agent。
- 完整 provider tokenizer。
- 复杂语义排序系统。
- 自动源码片段选择器。

先保证上下文链路能解释：

```text
本轮为什么召回这些记忆
为什么丢弃部分历史
为什么工具输出被压缩
哪些证据已经过期
当前 prompt 大概消耗多少预算
```

这比复杂但不可解释的上下文黑箱更适合当前项目定位。
